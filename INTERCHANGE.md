# Atelier packages

An **Atelier package** is a board, with every board nested in it, saved as one file that another person can add to their own workspace. It is the format for sharing work between people and for other tools that want to read or write Atelier boards.

| | Package | Workspace backup |
| --- | --- | --- |
| Holds | One board and everything nested in it | Every board in a workspace |
| File name | `Board-name.atelier.json` | `atelier-workspace.json` |
| Importing it | Adds its boards beside yours | Adds its boards beside yours, or replaces the workspace |
| Use it to | Share a piece of work | Move or restore your whole workspace |

Both are plain JSON, so they can be read, diffed, kept in version control and generated by scripts.

## In the app

- **Share a board:** open it, then **Export → This board · Atelier package**. The file carries the board, every board nested in it, and any board one of its cards opens.
- **Add someone's board:** **Export → Import a package or backup**, pick the file, then **Add to workspace**. The boards arrive at the top level of your sidebar and the first one opens. Nothing of yours is changed, and **Undo** takes the import back.
- **Keep working:** imported boards are ordinary boards. Every card can be edited, moved, restyled, connected or deleted, and the boards can be exported again as a new package.

Importing the same package twice gives two independent copies. Every board, card and connection gets a new ID on import, so a package never clashes with what is already in a workspace, including an earlier copy of itself.

## The file

```json
{
  "format": "atelier-package",
  "version": 1,
  "name": "Shot plan",
  "exported": "2026-10-11T00:00:00.000Z",
  "generator": "Atelier",
  "boards": [ { "id": "board-plan", "parent": null, "name": "Shot plan", … }, … ]
}
```

| Field | Required | Meaning |
| --- | --- | --- |
| `format` | yes | Always `"atelier-package"`. This is how a reader tells a package from a backup. |
| `version` | yes | The format version, currently `1`. |
| `boards` | yes | The boards, in the same shape as the `boards` of a workspace backup. At least one has `"parent": null`. |
| `name` | no | Shown when the file is imported. Defaults to the first top-level board's name. |
| `exported` | no | When the file was written, as an ISO 8601 time. Informational. |
| `generator` | no | What wrote the file. Informational. |

The full shape of a board, a card, a connector and a timeline is in [`schema/atelier-package.schema.json`](schema/atelier-package.schema.json) (JSON Schema 2020-12), with a description on every field. [`tests/fixtures/package.json`](tests/fixtures/package.json) is a small complete example that uses every kind of relationship.

### Rules a schema cannot check

A reader accepts a package only if all of these hold. Atelier checks them with the same code that checks a saved workspace, in the app and again in the desktop database.

- Board IDs are unique in the file, and card IDs are unique across all its boards.
- Every `parent` other than `null` names a board in the file, and nesting has no cycles.
- A board card's `boardId` names a board in the file.
- A connector's `from` and `to` name two different cards on its own board.
- A timeline item's `card` names a card on the timeline's own board that is neither a timeline nor a column. Positions are whole frames (timecode) or whole days since 1970-01-01 (date), within the timeline's range.
- Every table row is as wide as the first.

### What a package leaves out

Images, sketches, PDFs, 3D models and small videos are embedded in the card as data and travel with it. On the Mac, large originals dropped from Finder are kept in Atelier's own storage, and the card holds only a reference (`localAttachment`, `localVideo`) that means nothing on another computer. A package leaves those references out, and the card keeps its embedded preview. The export message says how many originals stayed behind. A package that still carries such a reference is accepted, and the reference is dropped on import.

## Versions

The format version changes only when an existing field changes meaning or a new field becomes required. Fields that older readers can ignore are added without a version change.

- A reader **rejects** a package with a higher version than it knows, and says so, rather than guessing.
- A reader **keeps** fields it does not recognise on a board, card or connector, so a newer file passes through an older Atelier without losing them.
- A writer always writes the lowest version that can hold what it saves.

## Writing packages from other tools

Generate the JSON, check it against the schema, and import it. The quickest start is to copy [`tests/fixtures/package.json`](tests/fixtures/package.json) and edit it. IDs in a package only need to be unique within that file; any short stable string (`[a-zA-Z0-9_-]`, up to 100 characters) will do, because Atelier assigns its own on import.

In JavaScript, `ui/interchange.js` does the work Atelier does: `pack(workspace, [boardId])` writes a package, `read(json)` checks a package or backup, and `graft(workspace, boards, uid)` adds boards under fresh IDs.
